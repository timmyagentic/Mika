# 正式版 Harness 详细 Trace 设计提案

Mika 把上下文发给模型，在手机上执行模型选择的工具，再把处理过的结果放进下一次请求。发生误操作或缓存命中量骤降时，需要检查这几步之间实际传递了什么。本草案提出在正式版增加一个默认关闭的「记录详细 Trace」开关。

## 本地运行中的缓存命中率

我在一台手机上检查了 10 次运行。主循环记录了 241 次模型回复，累计输入 21,874,709 个 Token，其中 7,767,040 个记录为缓存命中。按输入量加权，命中率为 **35.51%**。最长的一次运行有 78 步，累计有 6,918,005 个输入 Token 未计为命中。这里统计的是这批运行的主循环。旁路调用和重试有单独的合计口径。[运行统计](../../core/src/main/kotlin/com/wangzan101/mika/core/record/RunMetrics.kt)

现有 `model_reply` 记录每步用量，`compressed` 记录时间和折叠步数。遇到某一步命中量陡降，可以查它附近有没有折叠，却看不到两次实际请求从哪里开始不同。`prompt_version` 又按全部工具展开后的状态计算，同一版本内实际发送的工具列表仍可能变化。仅凭这些记录，很难判断该优化新加入的画面、已经发过的历史，还是继续核对服务商的用量报告。[现有事件](../../core/src/main/kotlin/com/wangzan101/mika/core/record/RunEvent.kt) · [工具展开与提示词版本](../../core/src/main/kotlin/com/wangzan101/mika/core/agent/AgentLoop.kt)

## 在手机上打开和查看

- 在 **设置 → 高级 → 运行诊断** 提供「记录详细 Trace」。开关默认关闭。开启时说明记录可能包含对话及屏幕内容，从下一次运行开始采集，连续复现多次也沿用该设置。
- 运行中显示「详细记录中」。关掉开关就停止采集，已落盘的部分可以查看。每次运行区分完整、部分记录，以及当时未开启记录。
- 在 **查看过程** 里沿用已有的步骤列表。展开一步可以看这一轮的请求原文、可见回复、工具执行和用量。点「与上一次比较」直接定位第一处变化。同一步的多次尝试分别列出。
- 已有运行可以通过 [#103](https://github.com/wangzan101/Mika/pull/103) 提议的入口导出当时保存的事件。详细 Trace 需要在复现时开启采集。

## 一次调用需要留下的证据

| 环节 | 详细 Trace 拟记录的内容 |
| --- | --- |
| 上下文 | 记录这次采用的模型、配置与用途，以及工具组展开、记忆加入、旧结果裁短、图片替换、历史折叠或因超长重试的触发条件。标出影响到的历史步号和改动前后大小，本地估算的 Token 数标为估算。 |
| 发送 | 在各模型适配器完成序列化的位置采集实际请求体。按发送时的顺序保留指令、工具定义、消息、工具结果和图片引用。每个块带类型、大小和内容指纹，能定位第一次变化发生在旧内容中，还是仅在末尾追加。 |
| 返回 | 将可见回复、工具调用、耗时、错误或取消与这次尝试关联。保留服务商返回的输入、输出、缓存读取量，以及可用时的缓存写入量。字段缺失显示「未上报」，显式零值显示为零。 |
| 执行与回填 | 用调用编号连起模型给出的工具参数、实际执行的动作、工具返回的结果，以及最终进入下一次请求的文字和图片。用户插话、取消或改用其他模型时，保留原尝试和后续尝试的关系。 |

每次实际发送分配本地编号，关联运行、步骤和尝试。默认比较同一运行中模型、用途及服务商配置相同的相邻请求。编号与采集时间只写入本地记录。模型适配器最清楚实际序列化了什么，Harness 则知道某条消息来自哪一步、为何被改写，两边用编号对应。[Responses 请求组装示例](../../core/src/main/kotlin/com/wangzan101/mika/core/model/ResponsesModel.kt) · [上下文处理与重试](../../core/src/main/kotlin/com/wangzan101/mika/core/agent/ModelCaller.kt)

例如，命中率下降时，如果旧块都相同，只在末尾新增了一张大图，同时缓存读取量仍接近上一轮输入，就可以优先检查新增画面的开销。如果第一处变化落在前几步的工具结果，且该次请求刚裁短过它，就可以针对这次裁剪做对照。若客户端可见的前缀一致而服务商报告的命中量下降，保留时间间隔和原始计数，原因标为待查。

## 保管和导出

只在开启时生成详细记录，存入本机应用私有目录。每轮按内容去重，连续步骤重复发送的历史或图片只写一份，各请求保存有序引用。设置单次及总容量上限，可按运行删除。中断、容量不足或写入失败时标出缺口，已写好的步骤仍可读取，任务继续按原有流程执行。

采集前排除鉴权头、Cookie、凭证参数和已识别的密码字段，查看内容时标明遮蔽位置。通过系统文件选择器导出选中运行或步骤，默认包只带事件顺序、用量和差异位置。正文和图片由用户分别勾选并预览后包含，导出的引用只带上所选范围用到的内容。

## 实现后的验收

1. 用固定模型回复、工具返回与画面跑同一脚本，比较开关打开和关闭时交给服务端的请求体、工具执行顺序和结果。普通路径的额外 Trace 写入应为零。
2. 分别构造只追加一张图、展开一组工具、裁短旧结果，以及同一步第一次请求失败后重试的场景。仅凭导出包应能定位首处差异、触发原因和每次尝试，区分「未上报」与零。
3. 复现一次连续点击同一按钮。沿记录能看到第一次点击是否生效、新画面是否进入第二次请求，以及模型在当时的输入下给出了什么动作。中途停录和达到容量上限时也能打开已写的部分。
4. 后续试验缓存优化时固定任务、模型、工具返回和画面，分别看首轮和连续步骤，比较加权命中率、每个任务未命中的绝对 Token 数、耗时及任务结果。
